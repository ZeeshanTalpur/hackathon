# Assumptions and data provenance

## 1. Data provenance - read this first

**All transport data in `supabase/seed.sql` is simulated for a hackathon demonstration.**

No verified real-world transport data was supplied, so none was used. Specifically:

| Invented | Notes |
| --- | --- |
| Route codes, names, corridors (`KHI-D1` ... `KHI-D5`) | Chosen to look plausible on a Karachi map. They do not correspond to any real route, operator or BRT line. |
| Stop-to-route assignments and stop ordering | Invented. |
| Distances between stops | Estimated from the straight-line geometry and rounded; not measured road distances. |
| Timetables, headways, first/last departure times | Invented. |
| Fares (PKR 55-80) | Invented. Not a real tariff. |
| Bus registrations (`DEMO-KHI-101` ...) | Deliberately non-real plate format. |
| Drivers, licence numbers, ratings, phone numbers | Fictional. Licence numbers use a `DEMO-LIC-*` prefix. |
| Passenger and staff profiles | Fictional. Emails use the reserved `.invalid` TLD so they can never reach a real mailbox; phones are placeholder `+92-300-00000xx` numbers. |
| All GPS positions | Generated by interpolating along the invented route geometry. No real vehicle was tracked. |
| Occupancy counts and delays | Invented to produce a useful demo. |

**Partially grounded:** stop *names* and *coordinates* are approximate positions of real,
well-known Karachi landmarks (Saddar, Numaish, Karsaz, Nagan Chowrangi, and so on), taken to about
four decimal places so the map renders believably. Treat them as approximate; they were not
surveyed, and the fact that a landmark is real does not mean a bus stop exists there.

If the team later obtains verified route or schedule data, it can be loaded into the same schema
by replacing `supabase/seed.sql`. Nothing in the schema depends on the demo values.

**Do not present any of this as real Karachi public transport information in the demo.** Label the
dataset as simulated in the UI.

## 2. Modelling assumptions

1. **A trip is the unit of live tracking.** One bus, one route, one direction, one departure. A bus
   running the route again later is a new trip row.
2. **Progress along a route is one number.** `trips.progress_km` drives everything else -
   `last_stop_order` and `next_stop_id` are derived from it, not maintained independently.
3. **Routes are polylines through their stops.** There is no separate shape/geometry table, so a
   route is drawn by connecting its stops in order. Positions are therefore straight-line
   interpolations, not road-snapped. Good enough for a demo map; a real deployment would add a
   shape table or use PostGIS.
4. **Delay is a signed number, not a status.** Positive is late, negative is early. The views treat
   `>= 5 minutes` as "delayed"; change that threshold in one place (`v_active_trips`,
   `v_fleet_status`) if the demo needs a different cut-off.
5. **Bus status and trip status are separate.** `buses.status` is the vehicle state
   (active / idle / maintenance / offline); `trips.status` is the service state. A bus can be
   `offline` with no trip at all, which is how the dataset demonstrates an untracked vehicle.
6. **Offline is detected by staleness, not by a flag alone.** `v_fleet_status.telemetry_stale` is
   true when the newest fix is older than 10 minutes, so the dashboard can flag a bus whose
   `status` column has not been updated yet.
7. **`bus_locations` is append-only** and nullable on `trip_id`, so a parked bus can still report a
   last known position. It is named `bus_locations` rather than `trip_locations` precisely because
   of that case; it is the location-history table the brief asked for.
8. **Timetables are offsets, not absolute times.** `route_stops.scheduled_offset_min` is minutes
   after the trip starts, so one route definition serves every departure of the day.
9. **Inbound is a mirror of outbound.** For `KHI-D1` and `KHI-D2` the inbound sequence is generated
   by reversing the outbound one and mirroring distances and offsets - it assumes the return
   journey takes the same path and the same time. `KHI-D3`, `KHI-D4` and `KHI-D5` are
   single-direction in the demo to keep the dataset small.
10. **No PostGIS.** Distance uses a `fn_haversine_km` helper so the project works on a plain
    Supabase instance with no extensions to enable.
11. **Fares are flat per route**, not distance-banded or zonal.
12. **`profiles.auth_user_id` is nullable and not a real foreign key** to `auth.users`. That is what
    lets the seed create demo users without creating Supabase auth accounts. When Member 1 wires up
    auth, a real user links itself by writing its `auth.uid()` into that column; add the FK later if
    you want the referential guarantee.
13. **Timestamps are `timestamptz`** (stored UTC). Karachi is UTC+05:00 with no daylight saving;
    render with `AT TIME ZONE 'Asia/Karachi'`.
14. **`service_date` is the local date the trip departs.** Trips that run past midnight are out of
    scope.

## 3. ETA assumptions

The ETA is deterministic arithmetic - there is no model, and none is planned at this stage.

- Speed is the latest reported non-zero speed, falling back to the route's planning speed
  (`routes.avg_speed_kmh`) when the bus is stationary or has no fix.
- Dwell time is a flat 0.5 minutes per intermediate stop.
- Traffic, time of day, weather and day of week are **not** considered.
- The estimate degrades gracefully rather than failing: a bus with no GPS fix still gets a
  schedule-speed ETA.

These are the weakest assumptions in the system and the obvious first thing to improve if the
project continues - for example by deriving per-segment speeds from historical `bus_locations`.

## 4. Security assumptions

Row level security is enabled on every table, but the policies are **demo-grade**:

- All transport data (routes, stops, buses, trips, locations, alerts) is readable by `anon`, because
  the passenger app is meant to work without logging in.
- `profiles` rows are visible only to their owner and to operators/admins; `drivers` requires
  authentication because the rows carry phone numbers and licence numbers.
- Any authenticated user can write to `trips`, `bus_locations` and `trip_stop_times`. That is too
  permissive for production and is only acceptable because the data is fake. The GPS simulator
  should use the `service_role` key, which bypasses RLS anyway.
- A commented-out block at the end of the RLS migration disables RLS entirely, as an escape hatch if
  policies block the demo and time runs out.

## 5. Scope boundaries

Deliberately **not** built, per the brief:

- No UI, maps, dashboards or auth screens.
- No GPS simulator. The seed produces a static snapshot of live state; the simulator comes later and
  can reuse `fn_route_point_at_km`.
- No ML or predictive analytics.
- No transfers in journey search - `fn_search_routes` returns direct routes only. A two-leg search
  would need a stop-to-stop graph walk, which is out of scope for the time available.
- No ticketing, payments, or passenger counting hardware.
- No historical rollups or materialised analytics tables. `trips`, `trip_stop_times` and
  `bus_locations` retain enough history for simple aggregate queries later.
- No real-time publication config. If Member 1 wants live updates, see the snippet in
  `supabase/README.md`.

## 6. Known limitations

- Re-running the seed `TRUNCATE`s every table, which would destroy real sign-ups. It is a demo
  reset script, not a migration.
- `trips.service_date` is derived from the trip's scheduled start, so seeding within an hour of
  midnight will produce trips dated across two days. Harmless, but worth knowing.
- `trip_stop_times.estimated_arrival_at` is a snapshot written at seed time. The live estimate comes
  from `v_trip_stop_eta`; nothing keeps the stored column fresh yet.
- Straight-line interpolation means a bus can appear to cut across a block between two distant
  stops. Adding intermediate shape points would fix it if there is time.
